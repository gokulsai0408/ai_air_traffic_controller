# What the system does: a 10-minute read

This is the whole system in plain language. For the detailed design, see [BUILD_PLAN.md](BUILD_PLAN.md). For the rules of the repo, see [CLAUDE.md](../CLAUDE.md).

## The problem

A thunderstorm cuts the arrival rate at Atlanta. A Delta flight is inbound, 45 minutes late. Its gate will be occupied when it lands. Two crew members are close to their duty limit. Thirty-one passengers have tight connections. The ramp shift ends at 21:00.

Today, three organisations sort this out by phone and radio:

- **Air traffic control (ATC)** owns the runway: separation between aircraft, how many land per hour, controller workload.
- **The airline (the pilot's side)** owns the aircraft: fuel, crew hours, connecting passengers.
- **Ground operations** owns the airport side: gates, ground-crew overtime, how fast the aircraft can turn around.

Each one optimises its own piece with partial information, and none of them can see the others' commercial data. The usual result is extra holding (fuel and CO₂), gate conflicts found only after landing, missed connections, crew timeouts, and delay that spreads to the aircraft's next flights.

The user we are building for is the **airline operations duty manager** at the hub, working with the arrival coordinator and the ramp lead.

## The idea in one sentence

**AI agents argue, code decides.** Three AI agents (ATC, Pilot, Ground) negotiate a fix, but every number, every legality check and every decision to stop comes from ordinary deterministic code, and a human signs off at the end.

That split is the whole design. Language models are good at reading messy text, proposing options and explaining themselves. They are bad at arithmetic and they can't be trusted to judge whether a plan is legal. So we never ask them to.

## What a "fix" looks like

A fix is one complete plan, picked from menus. It has four parts:

- a **runway slot** (a specific free arrival time),
- a **gate** (one of the airport's gates, or a remote stand),
- a **hold** (minutes spent circling before landing),
- or, instead of all that, a **divert** to another airport.

Agents can't invent a slot, a gate or an airport. If one names something that isn't on the menu, the plan is rejected on the spot. The action types are: land as planned, hold, regate, hold and regate, and divert.

## The data

The scenarios come from a real file: 358,774 delayed US flights from 2015 (the DOT on-time data). Every row is a delayed flight, so any row can become a live disruption. A judge can pick one at random.

The file doesn't have everything. It has no aircraft types, runway queues, gates, fuel, crew hours or connections. We **generate** those with a seeded random generator, so the same flight and seed always produce the same world. Every value is tagged:

- **REAL**: straight from the DOT data.
- **SYNTHETIC**: generated by us.
- **ASSUMED_CONST**: a constant we chose and have written down.

Synthetic values are never presented as real. That honesty is part of what we are judged on.

## The cast

| Component | Is it an AI? | What it does |
|---|---|---|
| World builder | No | Turns a data row into a full scenario, split into public facts, each agent's private facts, and a safety view. |
| **Safety kernel** | **No** | Checks every option against 12 numbered rules. The only thing allowed to say "this is safe". |
| Option generator | No | Builds the menu of possible plans. |
| Three agents | **Yes** (plus code) | Read the ops notes, propose plans, vote with reasons, and explain. Their costs come from their own code. |
| Coordinator | No | Runs the negotiation and decides when it ends. |
| Fallback | No | A fixed rule-based plan that is the answer when there's no deal. |
| Ledger | No | A tamper-evident log of everything that happened. |
| Duty manager | Human | Approves or overrides the final result. |

## One negotiation, step by step

**1. Set up.** The world is built from the flight row. The coordinator computes two reference plans: *do nothing* (original gate, first free slot, no coordination) and the *fallback* rule plan. Each agent works out what the fallback would cost it. That's its **walk-away point**: it won't accept anything worse than what the fallback already gives.

**2. Propose.** Each agent reads the situation and proposes one or two plans. It sees the public facts, its own private data, its own cost table and the menus. It never sees the other agents' private data.

**3. Filter.** Every plan, whether from a menu or an agent, goes through the safety kernel. Anything unsafe is dropped. **An unsafe plan never reaches a vote.** That is the central guarantee.

**4. Shortlist.** The coordinator keeps only plans that aren't worse for everyone than some other plan (a Pareto front), up to six, plus the agents' own proposals. It doesn't pick a favourite. It just removes plans that nobody should want.

**5. Vote.** Each agent votes ACCEPT or REJECT on each shortlisted plan, with a fixed reason code such as `FUEL_RESERVE` or `GATE_CONFLICT`. If everyone accepts a plan, that's a **consensus**, and the cheapest unanimous plan wins.

**6. Repeat, with a hard cap.** If there's no consensus, agents can counter-propose and the loop runs again. The number of rounds is capped (currently 3, and the team is deciding whether to make it 2, to match the brief's "under 3 turns"). The loop can't run forever.

**7. The final round is binding.** Votes stop mattering. The coordinator picks the cheapest plan that is acceptable to every agent, meaning no worse than their walk-away. An agent can block it only with a **checkable** objection, such as "this plan breaks my fuel limit", never with a preference. If there is such a plan, that's a **compromise**.

**8. Fallback and escalation.** If no compromise exists, the system uses the fallback plan, provided the kernel says it's safe. If even that is unsafe, the system **escalates**.

**9. Human sign-off.** The duty manager approves or overrides, and that action goes into the log too.

The four possible outcomes are **consensus**, **compromise**, **fallback** and **escalated**.

## The safety kernel

The kernel is the most important piece, so it's worth knowing what it checks. Each rule has an ID, a class, a source and a tag.

**Safety rules (never relaxed by anyone):**
- `C-RWY-01`: the runway slot is free and inside the arrival schedule.
- `C-WAKE-01`: enough time behind the previous landing, and before the next one, for wake turbulence. A heavy aircraft needs more space behind it than a medium one. The values come from ICAO and are converted to minutes at 140 knots (an assumed approach speed).
- `C-FUEL-01`: the aircraft still has its required reserve after holding. Our fuel figure is already *above* the 45-minute reserve, so the check is simply "extra fuel minus hold minutes is not negative".
- `C-FUEL-02`: for a divert, the aircraft can reach the other airport and still have its reserve.
- `C-CREW-01`: the aircraft is on its gate before the crew's duty period ends.

**Physical rules (can't be overridden, like two aircraft at one gate):**
- `C-SCHEMA-01`: the message is well formed and consistent with what it claims to be.
- `C-REF-01`: every slot, gate and airport named actually exists.
- `C-CONSIST-01`: the stated hold matches the chosen slot.
- `C-GATE-01`: the gate is big enough.
- `C-GATE-02`: the gate is free, with a 10-minute buffer.
- `C-TAXI-01`: the gate is reachable given taxiway closures from the ops notes.

**Policy rule (only a human may relax):**
- `C-POL-OT-01`: ground-crew overtime stays under a cap (15 minutes, assumed).

The kernel has some properties we test hard. It's **pure**: no network, no randomness, no AI, so the same input always gives the same answer. It **fails closed**: if it can't evaluate something, the answer is "unsafe". And extra information can only make it **stricter**, never looser.

## Private data and trust

Commercial data stays inside each agent. An agent shares only whether a plan is feasible for it, a cost, and a reason code. It never shares fuel figures, crew minutes or passenger counts. The kernel sees the *safety* data (fuel margins, crew limits, wake categories, gate occupancy) but not commercial data, much like a neutral airport-collaboration platform.

Free text is treated as untrusted. The ops notes (for example, "taxiway B closed, moderate turbulence in the hold") are read into a strict form with four fixed fields. That extraction can only **add** restrictions. There's no field that could say "ignore the fuel reserve", so a prompt-injection attack has nowhere to go. An agent's written rationale is for display only and is never read for decisions. Thresholds come only from `config/constraints.yaml`.

## When nothing works: declining on purpose

Sometimes no plan is safe and within policy. The system then does one of two things.

1. **If one policy rule is the only obstacle**, it finds the plan needing the smallest relaxation and asks the human for exactly that: *"Approve 25 minutes of ground-crew overtime (cap is 15). This enables slot S-14 at 20:52, gate B12."*
2. **If a safety rule is the obstacle**, it refuses and names the blockers: *"No safe plan within the model. The pilot-in-command and the controller must decide. Blocking: fuel reserve (margin −4 min)."* Safety rules are never offered for relaxation.

This is our planned visible failure case. The answer to "where does it fail, and how would your user know?" is that it fails when no option is safe, it says so, and the log shows why.

## The log, and proving nothing was changed

Every step is written to a **ledger**: a log where each entry includes a hash of the previous entry, like a chain. Change any entry and every hash after it breaks.

The command `python -m cdm.verify <log>` does three checks without calling any AI:

1. **The chain**: are all the hashes intact? If not, it names the first broken entry.
2. **The kernel replay**: rebuild the world and re-run the safety kernel on every logged option. Do the answers match?
3. **The decision replay**: re-apply the decision rules to the logged votes and costs. Is the same outcome reproduced?

A good run prints something like `CHAIN OK · KERNEL REPLAY 48/48 MATCH · DECISION REPRODUCED`. The demo moment is changing one byte in a log and watching verify fail at that entry.

Verify is deliberately honest about what it couldn't check. A step it can't run is reported as skipped, and a report whose option isn't in the log is marked "not replayable". It never counts a skipped check as a pass. One known gap: cutting entries off the very end of a log can't be detected by the chain alone.

## How we know it works (the evaluation)

The judges care about honest evaluation, so the plan is to measure, not to claim.

- **Baselines.** We compare against doing nothing, the fallback rule, a single AI given all the data in one prompt (the design the brief bans, labelled as a baseline), and a **central solver** that sees everything and picks the cheapest safe plan. The gap between us and the central solver is the "price of privacy", and we report it plainly.
- **Kernel ablation.** Random and deliberately hostile proposers replace the AI agents across about a thousand worlds. The target is **zero unsafe plans accepted**.
- **Red team.** At least 25 attacks: invented gates, plans directly behind a heavy aircraft, contradictory messages, malformed output, instructions hidden in ops notes, and agents voting yes on plans that are infeasible for them. One known weakness is stated up front: an agent that **lies about its own cost** isn't caught, because costs are self-reported.
- **Sensitivity.** Every synthetic or assumed number is varied by ±30% to see whether conclusions hold.
- **Cascade.** Using real aircraft rotations in the data (via tail number), we check a delay-propagation model against what actually happened. That figure is measured. The "after" figure for our plan is modelled, and labelled that way. The data only contains delayed flights, which biases the "before" figure, and we state that.

Every number on every slide is labelled **measured**, **modelled** or **assumed**.

## Where the work stands

Four people, four parts:

- **A** builds the data loader, the world generator, and the cost functions.
- **B** builds the safety kernel, the option menus, the fallback, and the ledger and verify.
- **C** builds the agents and the coordinator.
- **D** builds the baselines, the cascade, the evaluation, the dashboard and the pitch, and merges everyone's work.

As of this writing:

- **B's part is written and tested.** That is the kernel with all 12 rules, the options, the fallback, the ledger and the verify command, plus attack generators. It runs on A's real worlds: the tests build ATL worlds from the real flight file, and all the kernel's own attacks are caught on them. `verify` can rebuild a real world from nothing but a log and reproduce its decision.
- **A's world builder** is on the `integrated` branch together with B's work.
- **C's coordinator and rule-based agents** and **D's evaluation harness and dashboard** are on their own branches. The full pipeline has not been run with all four parts together, so there are no safety numbers to report yet.
- **One open safety issue** sits with C: ops facts read from the notes are not yet passed into the kernel, so a closure mentioned in the notes wouldn't yet block a gate.

## What to remember

If you remember five things:

1. AI proposes and argues. Code does the maths, the legality checks, and the stopping.
2. An unsafe plan can never reach a vote, and it can never become a decision.
3. Every agent keeps its commercial data private and shares only a feasibility flag, a cost and a reason code.
4. The loop always ends: capped rounds, a binding last round, then the fallback, then a request to the human.
5. Everything is logged in a tamper-evident chain that can be replayed without any AI.
